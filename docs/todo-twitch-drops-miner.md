## Контекст

TwitchDropsMiner — headless AFK-майнер timed Twitch Drops: GraphQL watch-events без скачивания видео/аудио, веб-дашборд (FastAPI + Socket.IO), cookies OAuth, приоритеты игр, история claim, встроенные Telegram-нотификации.

Ограничение апстрима: **один процесс майнера на один data directory / один Twitch-аккаунт** (не multi-tenant из коробки).

У бота уже есть другое: **алерты** по каталогу [twitchdrops.app](https://twitchdrops.app) (digest, стрим-алерты с тегом Drops) — без фарма. Майнинг не заменяет и не дублирует эту фичу 1:1.

Политика репо (`api-license-compliance`): не использовать неофициальный `gql.twitch.tv`. Майнер как раз на GraphQL watch — конфликт с текущими правилами.

## Два варианта развёртывания

### A. Веб-сервис на `bot.themarfa.name` + тонкий бот

- Фронт и бэк майнера — отдельный сервис (proxy / subdomain).
- В боте: кнопка перехода, авторизация через Telegram, оповещения (start/stop/status/claim).
- Бот не майнит.

### B. Вся работа на стороне бота

- Логин, настройки, статус, claim — в Telegram UI.
- Логика майнера внутри процесса бота или sidecar без отдельного UI для пользователя.

## Сравнение вариантов

| Критерий | A (веб + тонкий бот) | B (всё в боте) |
|----------|----------------------|----------------|
| Совпадение с TDM | Высокое: UI, device OAuth, приоритеты, история | Низкое: переписывать UX под чат |
| Multi-tenant | N изолированных воркеров + gateway | Тот же пул воркеров + нагрузка на bot |
| Изоляция сбоев | Падение майнера ≠ падение алертов | Общий процесс / память с прод-ботом |
| Безопасность | Cookies Twitch в отдельном сервисе | Токены рядом с основным ботом и БД |
| Масштаб | Горизонтально, отдельный хост | Упирается в bot-контейнер |
| UX настроек | Дашборд уже есть | Device-login и priority в чате почти непригодны |
| Ресурсы на 1 юзера | ~100–200 MB на воркер | То же + давление на bot |

## Рекомендация

| Сценарий | Решение |
|----------|---------|
| Текущий VPS, личный фарм 1 аккаунта | A как sidecar (mem_limit ~256m), не multi-user; лучше не смешивать с публичным путём бота без auth |
| Текущий VPS, фича для пользователей | **Не делать** без апгрейда |
| Более мощный VPS / отдельный хост, пользовательская фича | **Вариант A** |
| Вариант B | Только как личный/админ MVP; для продукта хуже по UX, изоляции и масштабу |

Мощность снимает лимит RAM, но не меняет архитектуру: упираемся в **N независимых воркеров**. UI почти всегда веб; бот — вход и пуши.

## Целевая схема (A, продукт)

```
Telegram-бот          → кнопка → Telegram Login → JWT/session
Gateway (наш код)     → квоты Premium, start/stop, статус, billing gate
Worker pool           → 1 контейнер/процесс на активного user (TDM или форк)
Notifications         → callback в основного бота (не BotFather-токен у каждого юзера)
Storage               → изолированный data-dir на user (cookies, settings); секреты не в логах
```

Бот не майнит. Стоковый TDM не multi-tenant — нужна обвязка (оркестратор + изоляция + auth).

## Блокеры (мощность VPS не снимает)

1. **ToS Twitch** — автоматизированный фарм через неофициальный GraphQL; риск для Helix-приложения и аккаунтов пользователей. Главный продуктовый блокер.
2. **Политика репо** — запрет `gql.twitch.tv`; фича требует явного исключения / решения owner.
3. **1 user ≈ 1 воркер** — даже на 8–16 GiB: десятки активных, не тысячи; нужен hard cap (Premium-слоты) и idle shutdown.
4. **Форк/обвязка** — не «просто docker run»; multi-tenant, Telegram Login, прокси, квоты — своя разработка.
5. Порт **8080** на VPS уже занят ботом — нужен reverse proxy / subdomain.

## Черновик этапов (если go)

1. **Spike** — 1 воркер TDM за proxy + Telegram Login stub; замер RAM/CPU 24h.
2. **Оркестратор** — start/stop по `user_id`, изолированный volume, health, hard cap.
3. **Бот** — кнопка, deep-link, статус, claim/error уведомления через основного бота.
4. **Premium / квоты** — gate + i18n (en/ru) + self_check на лимит.
5. **Ops** — mem/cpu limits, метрики, бэкап data-dirs, runbook при бане/429 Twitch.
6. **Docs** — user-facing ToS/risk notice; README attribution.

Не делать до go/no-go по ToS и выбора хоста.

## Не делать в рамках этой фичи

- Встраивать майнинг в процесс алертов / `check_streams` без изоляции.
- Отдавать пользователям настройку «свой BotFather token» (у TDM так из коробки) — использовать канал основного бота.
- Скрейп HTML Twitch / неофициальные пути сверх уже принятого риска GraphQL без явного решения.
- Запускать без `mem_limit` / без cap числа активных воркеров на shared VPS с ботом.
